My recent work has focused on building and testing the evaluation framework for the extraction pipeline. The extraction itself is now running, but the key challenge is how to evaluate the model output fairly, because the model may extract more records than the existing curated VecTraits data contains. So I separated the evaluation into different comparison layers and built a web interface to make the workflow easier to inspect and review.

The evaluation has two main comparisons.

Comparison A tests paper-faithfulness:
full model output is compared against my manual gold benchmark.

Comparison B tests curator-alignment:
after I manually select the rows that are suitable for VecTraits-style curation, this subset is compared against the existing curated VecTraits reference.

Then, review-adjusted evaluation is not a separate third comparison. It is a correction layer applied after A and B, where discrepancies can be manually labelled using fixed dropdown options.

This page stores the default reference files: the manual gold benchmark and the curated VecTraits reference. These are not uploaded every time; they are project-level references.

Here I can upload one or more PDFs, choose the model and prompt version, and start an extraction run. The page also shows per-paper progress, so I can see which papers succeeded or failed.

This page shows the full model output before evaluation. I wanted this step because I need to inspect what the model actually extracted before just looking at scores.

This page shows the automatic metrics. Comparison A uses the full model output against the manual gold benchmark. Comparison B uses the selected subset against the curated VecTraits reference.

This page is for review-adjusted evaluation. Instead of manually typing explanations, I use fixed dropdown decisions such as true model error, acceptable match, curator omission, unit equivalent, or row misalignment.

This page compares different runs across prompt versions and models. This is useful for prompt engineering because I can compare precision, recall, record-level F1, macro F1, and field-level performance across versions.

I am not relying on one score only, because different prompts fail in different ways. Some prompts over-extract and have high recall but low precision, while others are very precise but miss many valid records.

比如 Document Key Information Extraction 里，entity-level F1 是常见 evaluation metric；也就是把抽取出来的 key-value/entity 跟 gold reference 对齐，然后算 precision、recall 和 F1。

在 scientific text structured extraction 里，Dagdelen et al. 用 JSON schema 进行 NER/relation extraction，并报告 precision、recall 和 F1；他们还说明 performance 是基于 exact word-match 的 lower-bound metric。这个跟你现在的 schema-constrained extraction 很接近。

更广泛的 generative IE evaluation 也仍然把 precision、recall 和 F1 作为传统 foundational metrics，但会指出 generative outputs 可能需要 fuzzy/semantic matching 或 manual inspection，因为生成式模型的表达不一定和 reference 完全一致。

最近 complex PDF-to-JSON structured extraction benchmark 也强调类似思路：不同字段需要不同 correctness criteria，比如 identifiers 可以 exact match，quantities 可以 tolerance，names/phrasing 可以 semantic equivalence；arrays/records 需要 alignment，而且 omission 和 hallucination 要区分。

Transformer 的基本生成机制是 decoder output 经过 linear transformation 和 softmax 转成 next-token probabilities，所以它是一边看上下文一边预测下一个 token。 对 image 来说，Vision Transformer 这类方法通常会把图像切成 patches，再把这些 patches 投影成 embeddings，变成类似 token sequence 的形式让 transformer 处理。

The model generated structured records through schema-guided conditional generation. The input to the model was not the raw PDF file itself, but a paper-level evidence package containing article text, extracted tables, captions, figure legends and cropped visual evidence. Textual evidence, including the prompt, schema instructions, article text and table text, was tokenised and represented internally as text embeddings. Visual evidence, such as cropped figures or visually complex tables, was processed into image-derived embeddings or visual tokens. These textual and visual representations were then combined within the multimodal model, allowing generation to be conditioned on both document text and visual evidence.

During inference, the model generated the JSON output sequentially as text. Each output token was predicted conditionally on the prompt, the target schema, the evidence package and the tokens already generated. The schema guided the expected output structure by specifying the fields to be returned, while the document evidence provided the source information from which field values were inferred. The model therefore performed schema-guided conditional generation rather than rule-based extraction: it did not apply hand-coded extraction rules or store values in predefined variables, but generated schema-constrained JSON records using patterns learned during pre-training and instruction tuning \citep{vaswani2017attention,google2026gemma4modelcard}.
